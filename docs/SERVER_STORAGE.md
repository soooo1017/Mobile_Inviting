# 서버 저장 · 공유 방식 (2026-11-10 확정: 공유 중에만 자동 동기화)

> **상태: 확정 (2026-11-10)** — §13 참고. 아래 §2~§9는 검토 당시 기록이에요(경우의 수 · 삭제 · 보관 기간 등은 그대로 유효).
>
> 지금 상태: 초대장 내용 · 사진 · 음악은 **폰 안에만 저장**(자동 저장). 회원 정보(로그인)만 Supabase에 있음.

## 1. 왜 서버가 필요한가

- 게스트는 자기 폰에서 링크를 연다 → 만든 사람 폰이 꺼져 있어도 내용을 보여줄 곳이 필요.
- 참석 응답 · 방명록은 여러 게스트의 기록을 한 곳에 모아야 함.
- 내용을 고쳤을 때 이미 보낸 링크에도 반영되려면 링크가 항상 같은 곳을 봐야 함.

## 2. 공유 방식 경우의 수

| 방식 | 어떻게 | 좋은 점 | 아쉬운 점 |
|---|---|---|---|
| A. 폰만 사용 | 이미지 · PDF로 만들어 카톡 등으로 전송 | 서버 · 비용 없음 | 참석 응답 · 방명록 · 지도/전화 버튼 · 배경음악 · 감사페이지 자동 전환 모두 불가, 고치면 다시 보내야 함 |
| **B. 공유할 때만 올리기 (추천안)** | 편집은 폰에 저장, [공유하기 / 반영하기]를 누를 때만 글 · 사진 · 음악을 서버에 올림. 응답 · 방명록만 게스트가 서버에 직접 남김 | 지금 구조를 거의 안 바꿈, 서버 쓰기 양 적음, 오프라인 편집 가능 | 고친 뒤 [반영하기]를 눌러야 게스트에게 보임 |
| C. 항상 동기화 | 고칠 때마다 서버에도 저장 | 다른 기기에서 이어서 편집, 폰 분실에 안전 | 구현 · 비용 부담 큼, 미완성 내용 노출을 따로 막아야 함 |

서버를 직접 운영할 필요는 없음: **Supabase(관리형) + 무료 웹 호스팅(GitHub Pages 등)**.

## 3. 저장 위치

| 무엇 | 어디에 |
|---|---|
| 초대장 글 · 설정 | Supabase Database |
| 사진 · 음악 | Supabase Storage (`초대장ID/…` 폴더, 글에는 파일 주소만) |
| 참석 응답 · 방명록 | Supabase Database |

게스트는 보기만, 올리기 · 지우기는 만든 사람만. 사진은 올리기 전에 폰에서 줄이기(장당 약 0.3MB).

## 4. 삭제 경우의 수

| 경우 | 폰 | 서버 | 링크를 열면 |
|---|---|---|---|
| 사용자가 삭제 | 삭제 | 글 · 사진 · 음악 · 응답 · 방명록 모두 삭제 | "삭제된 초대장이에요" |
| 인터넷 없이 삭제 | 바로 삭제 | 다음 연결 때 삭제 | 처리 전까지는 보일 수 있음 |
| 보관 기간 끝남(행사일 + 1년, 자동) | **남김**(지난 행사, 열기 · 고치기 가능) | 하루 한 번 예약 작업이 삭제 | "삭제된 초대장이에요" (그 전 감사페이지 기간이 끝난 뒤엔 "행사가 끝난 초대장이에요") |
| 보관 기간 끝난 뒤 다시 공유 | 그대로 | 폰 내용으로 새로 올림 | 다시 열림 |

함께 챙길 것: 응답 · 방명록을 폰에도 복사(삭제 직전 한 번 더), 삭제 전 앱 안 안내("30일 뒤 · 7일 뒤 서버에서 삭제돼요"), 개인정보처리방침에 보관 기간, 서버 삭제 뒤엔 폰이 유일한 사본.

## 5. 보관 기간 (2026-10-27 확정: 행사일로부터 1년)

- **초대장 자체(글 · 사진 · 음악) + 참석 응답 + 방명록은 행사일로부터 1년 동안 서버에 보관하고, 그 뒤 자동 삭제**해요(하루 한 번 예약 작업).
- 게스트가 링크로 보는 기간은 따로예요: 행사일 → (감사페이지를 쓰면 행사 다음 날부터 1~7일) → 그 뒤 링크는 "행사가 끝난 초대장이에요" 안내. 만든 사람은 보관 기간 동안 관리 화면에서 응답 · 방명록을 보고 내려받을 수 있어요.
- 삭제 전: 앱 안 안내(예: 30일 전 · 7일 전 "곧 서버에서 삭제돼요 — 데이터 내려받기") + 폰에는 초대장이 남아요(다시 공유하면 새로 올림).
- 개인정보처리방침 3항에 이 보관 기간을 적어 뒀어요.
- 유료 연장 · 보관 기간 선택은 이번 출시에서 논의하지 않아요(2026-10-27).

## 6. 비용 감각 (대략 — 착수 시 요금표 재확인)

무료 플랜 파일 약 1GB · 월 전송 약 5GB · 파일당 약 50MB, 일주일 미사용 시 일시 정지. 초대장 하나(사진 30장 줄인 것 + 음악) 약 15MB → 약 60개. 늘어나면 유료(월 약 25달러) 또는 다른 저장소 검토.

## 7. 함께 보류되는 작업

서버 저장 → 게스트 화면(D) → 공유하기(C). 관리 화면(E)은 화면을 먼저 만들어 두고(2026-10-20), 응답 · 방명록 · 방문 수는 서버 연결 전까지 0으로 보여줌(`mobile/src/state/guestData.ts` 한 곳만 바꾸면 연결됨).

## 8. 방문 통계

방문한 사람(같은 기기 · 브라우저는 1명) · 열어본 횟수만 익명 숫자로 셈. 사람별 방문 기록이나 추가 지표(경로 · 누른 버튼 등)는 넣지 않기로 함(2026-10-20). 개인정보처리방침에 수집 사실을 적어 둠.

## 9. 링크는 초대장을 만들 때 생성 (2026-10-23 확정)

QR 코드 · 홍보물(`docs/POSTER_QR.md`)을 공유 전에도 미리 만들어 보게 하려고, **링크 주소(ID)는 초대장을 만드는 순간 정해지고, 공유를 시작하기 전까지만 바꿀 수 있어요(시작하면 영구 고정).** 서버를 붙일 때 챙길 것:

- 초대장 행을 만들 때 링크용 ID(slug)를 같이 저장하기 — 앱이 `Project.link.slug`로 만들어요(자동 랜덤 8자 / 문구 + 랜덤 4자, `mobile/src/share/link.ts`). 서버에는 slug **유니크 제약**을 걸고, 겹치면 랜덤 글자를 다시 뽑아요. 공유를 시작(`locked`)한 slug는 서버에서도 바꾸지 못하게 막아요.
- 공유를 시작하기 전(작성중)에 링크를 열면: **초대장 주인**(로그인한 상태)은 진짜 초대장 미리 보기(위에 "나만 볼 수 있어요" 띠), **다른 사람**은 "아직 준비 중인 초대장이에요" 화면 + [초대장 주인이신가요? 로그인하고 미리 보기].
- 링크 · QR이 이미 밖에 나가 있을 수 있어서, 공유 시작 전 방문은 **방문 통계에 세지 않기**.

## 10. 문의 접수와 운영자 답변 (2026-10-25)

- 앱 문의는 Supabase `inquiries` 테이블에 저장해요(`supabase/schema.sql` 8번). 로그인한 본인 문의만 읽고 쓸 수 있고(RLS), `status`·`reply`·`replied_at`는 운영자만 채워요.
- **관리자 페이지는 앱 안에 두지 않아요.** 지금은 Supabase 대시보드(Table Editor)에서 `reply`를 적고 `status`를 `answered`로 바꾸면 사용자의 문의내역에 "답변 완료"로 보여요.
- 문의가 많아지면 **운영자용 웹 페이지**(별도 도메인 + 관리자 로그인)를 따로 만들어 답변 · 상태 관리를 옮겨요. 이때는 관리자만 모든 문의를 읽고 답변할 수 있는 정책과 알림(새 문의 메일)이 필요해요.

## 11. 서버 구성 결정 (2026-10-25)

- **서버를 직접 운영하지 않아요**(집 서버 · 직접 구축 X — 정전 · 보안 · 백업 부담). 관리형 서비스를 써요.
- **DB · 로그인 · 사진 · 음악 보관 = Supabase**, **게스트 웹 페이지(+ 카톡 미리보기용 서버 코드) = Vercel**. 무료로 시작하고 사용자가 생기는 시점에 유료로 올려요(Supabase Pro 월 약 25달러 ≈ 3.5~4만 원 — 무료는 일주일 미사용 시 일시정지). Vercel 무료(Hobby)는 비상업 조건이 있을 수 있어 정식 출시 전에 요금 조건을 확인해요.
- **링크 주소**: 처음엔 Vercel 기본 주소(`프로젝트이름.vercel.app/i/<뒷부분>`)로 시작하고, 사용자가 늘면 **내 도메인을 사서 같은 Vercel 프로젝트에 연결**해요. 이미 공유한 `vercel.app` 링크는 그대로 열리고 새 초대장부터 새 도메인을 써요(옛 주소는 초대장이 만료될 때까지 유지). 주소는 `link.ts` 한 곳에서만 만들어요.
- 앱 이름이 정해지면 Vercel 프로젝트 이름 · 도메인 이름을 같이 정해요.

## 12. 배경음악 음원 파일 (2026-11-08)

- 앱이 제공하는 곡의 음원 파일(`bgm001.mp3` …)은 저작권 · 용량 때문에 **git에 올리지 않고** Supabase Storage 공개 폴더(`bgm`)에 올려요. 앱과 손님 웹페이지가 같은 주소를 불러와 재생해요.
- 앱 설정: `mobile/.env`의 `EXPO_PUBLIC_BGM_BASE_URL`(폴더 주소, 끝에 `/` 없이). `.env.example`에 자리가 있어요. 곡 정보(이름 · 출처 · 라이선스 · 파형)는 앱 코드(`editor/bgm.ts`)에 있어서 곡을 추가할 때만 앱을 새로 배포해요 — 곡이 많아지면 DB 테이블로 옮기는 걸 검토.
- 사용자가 올린 "내 음악"은 지금은 폰 안의 파일 주소로만 저장돼요 — 서버 저장 단계에서 Storage로 올리고, 초대장 삭제 · 보관 기간 후 삭제와 같이 지워요.
- **출시 전 할 일**: 확정한 곡의 앱용 파일을 `bgm` 폴더에 업로드(공개 읽기) → `.env`에 주소 입력 → 기기에서 ▶ 재생 확인.

## 13. 확정: 공유 전엔 폰, 공유 중엔 자동 동기화, 끝나면 다시 폰 (2026-11-10)

**방식** (B안 + 공유 중에만 C안): 아래 "서버" = Supabase, "하객 페이지" = Vercel.

| 시점 | 기준이 되는 곳 | 어떻게 |
|---|---|---|
| 공유 전(작성 중) | **폰** | 서버에는 아무것도 없어요. 링크 · QR · 홍보물은 미리 만들 수 있고, 링크는 모두에게 "아직 준비 중인 초대장이에요" |
| [공유 시작] | 폰 → 서버 | 사진 · 음악을 Storage에 올리고 초대장을 `invitations`에 저장. 링크가 열려요 |
| 공유 중 | **폰이 원본, 고칠 때마다 서버에 자동 반영** | 고치고 잠시(약 2초) 뒤 서버에 올려 링크에 바로 적용. 인터넷이 없으면 쌓아 두었다가 연결되면 올리고, 화면에 "반영 중 · 반영됨 · 오프라인" 표시 |
| [공유 중지] | 폰 | 자동 반영을 멈춰요. 링크는 "공유가 끝났어요"로 바뀌고, 서버의 초대장 · 응답 · 방명록은 **보관기간(행사일 + 1년) 동안 남아** 관리 화면에서 볼 수 있어요 |
| 다시 [공유 시작] | 폰 → 서버 | 폰 내용으로 서버를 덮어써 새로 올려요(링크는 그대로) |
| 보관기간 끝남 | 폰 | 서버에서 자동 삭제(§5). 폰에는 초대장이 남아요 |

- 동기화는 **폰 → 서버 한 방향**이에요. 다른 폰에서 이어서 고치기(양방향)는 지금 하지 않아요. 나중에 넓힐 수 있게 표 구조는 그대로 둬요.
- 공유 중에 고친 내용은 곧바로 하객에게 보여요. 쓰다 만 내용이 보이지 않게, 앱에서 "반영 중" 표시와 [공유 중지]를 가까이 두는 걸 UI에서 챙겨요.
- 주소(slug)는 처음 올린 뒤로 못 바꿔요(서버가 막아요). 올릴 때 겹치면 랜덤 글자를 다시 뽑아요(공유 전이라 QR을 아직 안 퍼뜨렸다는 전제).

**표** (`supabase/schema.sql` 9번, Supabase SQL Editor에서 한 번 실행):

| 표 | 내용 |
|---|---|
| `invitations` | 공유를 시작한 초대장만. 주소 · 제목 · 행사 · 내용(JSON) · 감사페이지(JSON) · 상태(공유 중 / 중지) · 삭제 예정일(서버가 계산) |
| `rsvp_responses` | 참석 응답. 같은 기기가 다시 보내면 덮어써요 |
| `guestbook_posts` | 방명록. `secret`이면 하객에게 안 보여요 |
| `invitation_visits` | 방문 통계(익명 기기 번호 · 횟수) |
| Storage `invitation-media` | 사진 · 내 음악. 경로 `<만든 사람 id>/…`, 읽기는 공개 주소, 올리기 · 지우기는 자기 폴더만 |
| Storage `bgm` | 앱이 제공하는 배경음악(운영자가 직접 올림) |

**보안**: 하객(로그인 없음)은 표를 직접 못 읽고, 함수로만 한다 — `get_public_invitation` · `submit_rsvp` · `post_guestbook` · `list_guestbook` · `record_visit`. 만든 사람은 자기 초대장의 응답 · 방명록 · 통계만 읽을 수 있고(RLS), 방명록 글을 지울 수 있어요. 한 기기가 한 초대장에 한 시간 5번까지만 남길 수 있어요(스팸 방지, 문제가 생기면 봇 차단 추가).

**검증**: 임시 Postgres에서 schema.sql 전체를 두 번 실행(이미 있어도 오류 없음)하고, 공유 중 / 중지 / 만료 / 남의 초대장 / 하객 직접 접근 / 속도 제한 / 만료 삭제(응답 · 방명록 함께 삭제)를 시험했어요. 실제 Supabase에서는 아직 실행 전이에요.

**아직 안 한 것**: 앱의 [공유 시작] 올리기 · 자동 반영 · 상태 표시, 하객 페이지가 초대장을 읽어 그리기, 응답 · 방명록 화면, 만료 시 사진 · 음악 파일 삭제(Edge Function), `pg_cron` 켜기.
